# 1. Why AI Coding Deserves Your Attention

In early November 2026, I typed one request to GitHub Copilot in VS Code:

```text
Create a set of prompts that will allow julia to be used as a programming language with the
[godot](https://godotengine.org/) platform. The julia language support must match the current
capabilities implemented for C#/.Net.
```
Notice that I did **not** request code, I asked for **prompts**. A plan the agent 
can execute later, one step at a time. The agent's answer in `.github\prompts` contained:

- A shared instructions file,
- a C#-to-Julia comparison table with about a hundred rows,
- eighteen numbered phase prompts.

I did not write any code myself at this point, I just reviewed the prompts 
generated by the agent, making sure I understood each step, while making some 
minor adjustments to the prompts before moving on.

From there, I ran the same short command over and over: `/gdjl-00-next`. It 
means "find the next unfinished phase and do it."

This book explains how Copilot interpreted the prompts and turned them into a 
working Godot-julia integration, demonstrating how AI can be used for a 
real-world advanced software development project.


## What I Built using AI

First, some quick context.

- [Godot](https://godotengine.org/) is a popular open-source game engine.
- Out of the box, it supports two scripting languages: its own **GDScript** and, 
  through a separate .NET build, **C#**.
- **Godot-julia** adds [Julia](https://julialang.org/) as a third. Its goal is 
  to match the C# support feature for feature.

Here's what the repository you're reading contains today:

- **A complete generated engine API.** 1036 classes, 16.8k methods and 4162 
  properties, with none skipped ([parity matrix row 2.1](../csharp-parity-matrix.md)). 
  A generator in [`julia/GodotBindgen/`](../../julia/GodotBindgen) produces 
  it from Godot's machine-readable API description.
- **A native host** in [`native/`](../../native). It's a thin C++ GDExtension that 
  loads the Julia runtime into an unmodified, official Godot 4.7.2 editor 
  ([ADR 0000](../adr/0000-gdextension-vs-module.md), [ADR 0002](../adr/0002-runtime-loading.md)).
- **Julia as a real Godot script language.** `.jl` files attach to nodes just like C# scripts. You get ([README](../../README.md)):
  - exported properties with every inspector hint,
  - signals, global classes and RPC,
  - `async`/`await` on signals,
  - hot reload with state preserved,
  - a *Build* button and panel in the editor,
  - script templates and syntax highlighting,
  - error reporting in Godot's debugger,
  - desktop exports with the scripts compiled ahead of time.
- **Fifteen architecture decision records** in [`docs/adr/`](../adr), ADR 0000 to ADR 0014. Each one records a decision the agent made or was asked to make, and why.
- **Eleven headless integration-test projects** in [`tests/integration/`](../../tests/integration). On top of those: unit tests, golden math tests generated by Godot itself, export tests, benchmarks, and one command that runs everything: `julia scripts/test_all.jl`.
- **A user guide** in [`docs/user/`](../user/README.md), with one page for each page of Godot's C# documentation. A doc test executes every Julia code block in it.
- **Five demos** in [`demos/`](../../demos/README.md). These are Julia ports of the official C# demos *Dodge the Creeps*, *Pong*, *Squash the Creeps* and *Multiplayer Pong*, plus an editor-plugin demo written in Julia. Each one runs headlessly as part of the test suite.

Now the scoreboard. The [parity matrix](../csharp-parity-matrix.md) tracks 102 capabilities:

| Status | Rows |
|--------|------|
| `DONE` | 92 |
| `PARTIAL` | 5 |
| `TODO` | 4 |
| `GAP` | 1 |

The matrix rule is strict. A row may only be `DONE` if code exists **and** a test that exercises it passes. Since phase 15, a script enforces that rule: [`scripts/check_parity_tests.jl`](../../scripts/check_parity_tests.jl).

## A Script, Before and After

Let's see what this looks like to you as a game developer.

The official C# version of the player in *Dodge the Creeps* begins like this ([godot-demo-projects, `mono/dodge_the_creeps/Player.cs`](https://github.com/godotengine/godot-demo-projects/blob/master/mono/dodge_the_creeps/Player.cs), MIT):

```csharp
public partial class Player : Area2D
{
    [Signal]
    public delegate void HitEventHandler();

    [Export]
    public int Speed { get; set; } = 400; // How fast the player will move (pixels/sec).

    public Vector2 ScreenSize { get; set; } // Size of the game window.

    public override void _Ready()
    {
        ScreenSize = GetViewportRect().Size;
        Hide();
    }
```

Here's the Julia port that ships in this repository ([`demos/dodge_the_creeps/Player.jl`](../../demos/dodge_the_creeps/Player.jl)):

```julia
# Ported from godot-demo-projects mono/dodge_the_creeps/Player.cs (MIT, Godot contributors).
using Godot

@godot_class mutable struct Player <: Area2D
    @signal hit()
    @export speed::Int = 400        # How fast the player will move (pixels/sec).
    screen_size::Vector2 = Vector2_ZERO   # Size of the game window.
end

function Godot._ready(self::Player)
    self.screen_size = get_viewport_rect(self).size
    hide(self)
end
```

The collision handler from the same file shows two more things:

- the generated, per-signal helper `emit_hit`,
- a deferred property write.

```julia
function on_body_entered(self::Player, body::PhysicsBody2D)
    hide(self)  # Player disappears after being hit.
    emit_hit(self)
    # Must be deferred as we can't change physics properties on a physics callback.
    set_deferred(get_node(self, "CollisionShape2D"), :disabled, true)
end
```

Read the two files side by side. They match line for line. That's deliberate.

Behind those dozen lines of Julia sits a lot of machinery:

- an embedded language runtime,
- two garbage collectors that must agree on who owns what,
- thread adoption,
- a script-language implementation inside Godot's editor,
- a bindings generator.

The rest of this book shows you how we specified, built and verified that machinery, with an AI agent doing most of the typing.

## How It Was Actually Driven

It's tempting to tell this kind of story as if it were magic. It wasn't. The recorded Copilot session history for this repository gives you a far more useful picture.

**The timeline:**

- The phase work spans sessions on **2, 4 and 5 November 2026**. Nothing is recorded on 3 November.
- By the evening of 5 November, the agent was finishing phase 16, with 11 of 11 integration projects passing their leak checks.
- The sessions on 9 November dealt with licensing and naming.

**The conversation:** the main session has **51 turns**.

- 17 of them are the single command `/gdjl-00-next`.
- One is `/gdjl-01-scaffold`.
- 10 more are VS Code's *Continue to iterate?* confirmation. It appears after the agent has worked autonomously for a long stretch.
- 16 are notifications from long-running terminal commands (builds, test runs, exports). VS Code passed them back to the agent when they finished.

Very few turns contain hand-written guidance. The most important one is a **scope decision**:

`/gdjl-00-next skip and remove 10.3, 10.4 and 10.5`

Those were the Android, iOS and Web export rows. The agent removed them from the parity matrix and from the phase 14 prompt, and kept going.

A word of caution about these numbers. They count conversation turns, not effort.

- A single turn often covered an hour or more of agent work: reading Godot's C# sources, writing code, building, running tests, and fixing what failed.
- The numbers say nothing about how much we read and reviewed between turns.

Still, the shape is clear. **We** set the destination and the rules, made the scope calls, and kept the loop running. **The agent** did the long, detailed middle.

This book is written around GitHub Copilot in VS Code with Claude Opus 5.5. The techniques aren't tied to one model. We describe them so you can carry them over to other frontier models, and to future ones.

## What Changed: From Autocomplete to Agents

You probably met AI coding through **autocomplete**: a grey suggestion finishing the line you were typing.

Then came **chat**: paste some code, ask a question, copy the answer back.

Both are useful. Both also keep *you* in the inner loop. You write, you run, you read the error, you ask again.

An **agent** closes that inner loop itself. In VS Code today, the agent can:

- read and search your whole workspace, not just the snippet you pasted;
- fetch reference sources from the web, such as a specific file of Godot's C# implementation at a pinned release tag;
- edit many files in one task;
- run builds, tests and scripts in a terminal, read the output, and try again;
- keep notes that survive between sessions, and follow project-wide instructions it reads at the start of every chat.

Here's the key insight: raw model intelligence isn't what makes this project possible. The decisive factor is the **feedback loop**.

Compare these two:

- A model that writes a plausible FFI binding is a curiosity.
- A model that writes the binding, runs `julia --project=julia/Godot -e "using Pkg; Pkg.test()"`, sees a nonzero allocation count where the requirement says zero, finds the boxed value, and fixes it is a colleague.

That's exactly why every phase prompt in this repository ends with tests and "done when" criteria. They give the agent an **oracle** it can consult without asking you.

## What Did Not Change

The agent wrote most of the code in this repository. It did **not** take over responsibility for it.

Several jobs stayed with us. You'll see them called out in every chapter:

- **Choosing the goal.** "Match C#" is a human decision. It's also a very good one, as chapter 2 explains. It turns an open-ended design problem into a port with a public reference.
- **Setting the rules.** The [project instructions](../../.github/copilot-instructions.md) fix the architecture ("change only via an ADR") and the non-negotiable conventions. For example:
  - no Julia exception may unwind through C++ frames,
  - C++ never holds a Julia value without pinning it,
  - generated code is never edited by hand.
- **Making scope calls.** Removing mobile and web exports. Accepting that `juliac --trim` isn't feasible for an eval-based script runtime ([ADR 0014](../adr/0014-export.md)). Deciding when `PARTIAL` is good enough for now.
- **Verifying and owning.** Reading the reports, spot-checking the code, and running the manual checks that can't be automated, such as attaching VS Code's debugger to a running game ([`docs/debugging.md`](../debugging.md)).

Worried that agents will make developers obsolete? This project offers a more nuanced data point. The work that stayed human was smaller in volume. But it was the work that decided whether the result was any good.

We'll leave the larger debate there. This book is about craft.

## The Honest Ledger

A book like this is only useful if it's honest about friction. So here's a preview of the bumps you'll meet in later chapters.

The agent's own tests or a run of the engine found each one. Each one got fixed.

- **A prompt that was simply wrong.** The phase 2 prompt asked for `jl_atexit_hook(0)` at shutdown.
  - In practice, that call suspends every other Julia thread, including engine threads Julia had adopted.
  - Godot then hangs forever when it joins them at exit.
  - The fix and the reasoning live in [ADR 0010](../adr/0010-signals-async.md) and in a comment in [`native/src/julia_host.cpp`](../../native/src/julia_host.cpp).
  - **Lesson:** prompts are hypotheses; reality gets the last word (chapters 5 and 13).
- **A name that meant two things.** Inside the generated `Godot` module, Godot's own `WeakRef` class shadows Julia's `Base.WeakRef`.
  - A call meant for Julia constructed a Godot object instead, and recursed until the stack overflowed.
  - Package code now always writes `Base.WeakRef` ([`julia/Godot/src/object/lifetime.jl`](../../julia/Godot/src/object/lifetime.jl); chapters 7 and 10).
- **A bug that waited for a later phase.** Objects created from Julia never received Godot's `NOTIFICATION_POSTINITIALIZE`.
  - Nothing visibly broke until phase 12, when Julia-created editor docks crashed.
  - The fix landed then, and the parity matrix records the history in row 4.1 ([ADR 0012](../adr/0012-editor-integration.md); chapters 10 and 15).
- **A tool that mangled text.** Late in the project, a PowerShell rewrite of a documentation file turned `→` into `â†’`.
  - The agent noticed and fixed it.
  - **Lesson:** the tools between the agent and your files have opinions about encodings.

The parity matrix itself is part of the ledger. Its five `PARTIAL` rows exist because the rules don't allow optimism. They stay `PARTIAL` until evidence exists:

- CI workflows that have never run on GitHub (the repository isn't published yet),
- Linux and macOS exports that are implemented but not yet executed,
- two debugger checks that need a human at the keyboard.

Ahead-of-time trimming turned out not to be feasible, so row 10.6 is a `GAP` with a written justification ([ADR 0014](../adr/0014-export.md)). And the final audit added four `TODO` rows for capabilities it found missing (chapter 20).

You want an agent that leaves a row `PARTIAL` rather than one that rounds up. Much of this book shows you how to build that discipline into your prompts.

## Why This Project Is a Good Teacher

Plenty of AI coding demos build a to-do app. This project is useful for learning precisely because it's **not** easy:

- **It's low-level and unforgiving.** FFI over a C interface, memory layouts that must match byte for byte, two garbage collectors, foreign threads, shutdown ordering. Mistakes crash the editor. They don't just render a button in the wrong color.
- **It spans the whole lifecycle.** Scaffolding, runtime, API generation, language semantics, editor tooling, debugging, packaging, CI, documentation and demos. Every kind of software engineering task shows up in at least one phase.
- **Its success criteria are objective.** Godot's C# support is public, versioned and well documented. So "Is it done?" has an answer you can check.
- **It was built in the open, prompt by prompt.** Every prompt the agent followed is in [`.github/prompts/`](../../.github/prompts), right next to the code it produced. You can rerun any of them yourself.

That last point comes with a big caveat.

Copilot did remarkably well here, and part of the reason is that Godot is the kind of codebase agents thrive on. Many real-world codebases aren't like that. Chapter 2 compares this repository with a private enterprise portfolio. It explains what makes the difference, and what you can do about it in your own code.

## Who This Book Is For

- **You're a developer** who has used chat-based AI assistants. You want to run longer, multi-step, mostly autonomous work without losing control of quality.
- **You're a technical lead** deciding how your team should adopt coding agents: what to standardize (instructions, specs, tests), what to review, and where the risks are.

You don't need to know Godot, Julia or GDExtension. Each chapter explains the domain concepts it uses, but only to the depth the AI-coding lesson needs.

### What You Need to Follow Along

The exercises use this repository. To run them, install what the [README](../../README.md) lists:

- the pinned Godot editor (4.7.2-stable, see [`GODOT_VERSION`](../../GODOT_VERSION)),
- Julia 1.12 or later,
- Python with SCons,
- a C++ toolchain,
- VS Code with GitHub Copilot.

Many exercises only ask the agent to *explain* or *plan* something, using the Ask or Plan agent. For those, a clone of the repository is all you need.

## Your First Step

Don't wait until the end of the book to try this.

By the end of chapter 3, you'll have seen the three artifacts that do most of the work:

1. a **project instructions file**,
2. a **status matrix** with a strict definition of done,
3. a **resumable driver prompt**.

Here's your challenge:

1. Pick a small, real task in your own codebase. Ideally, choose one with an existing reference to match.
2. Write those three files for it. Keep them short.
3. Let the agent take the first step.
4. Read what it reports.

That's how this project started: one request, a plan, and a command to keep going.
