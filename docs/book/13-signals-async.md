# 13. Signals and Async: Translating a Concurrency Model

Godot games are **event-driven**. A button emits `pressed`, a timer emits `timeout`, an animation emits `finished`, and your scripts react.

In GDScript you write `await timer.timeout`. In C# you write `await ToSignal(timer, "timeout")`. Either way, the code *reads* sequentially while the engine keeps running frames in between.

Behind that convenience sits a **concurrency model**. Here's how C# handles it:

- Every `await` continuation goes through a `SynchronizationContext` that Godot drains once per frame *on the main thread*. So code after an `await` can touch the scene tree safely.
- Signal handlers are delegates. A delegate whose target object has been freed is disconnected automatically.
- `Task.Run` work goes to thread-pool threads that the .NET runtime attaches for you.

Phase 10 translates all of that into Julia. And Julia has its own concurrency model:

- lightweight `Task`s,
- a scheduler,
- `wait`/`notify`,
- real OS threads via `Threads.@spawn`.

The translation has to respect both models. Godot's rule is that the scene tree belongs to the main thread. Julia has its own rules for tasks, threads and garbage collection.

In this chapter you'll see how the prompt pins down the hard parts by naming the C# classes that already solve them. You'll also see how the phase exposed two deep bugs in the foundations laid in phase 2.

The phase builds on earlier work:

- Callables (chapter 9),
- the object model with its release queue (chapter 10),
- the script language's per-frame `_frame` hook (chapter 11).

Later, hot reload (chapter 14) must keep signal connections alive across reloads.

```markdown
## Requirements

1. **Signal value type**: `Signal(obj, :name)` with `connect`, `disconnect`, `is_connected`, `emit`, `get_connections`.
2. **Connecting**: `connect(obj, :timeout, f; flags = ConnectFlags(...))` where `f` is any Julia callable, including closures and bound methods (`Callable(self, :on_timeout)`); returns the `Callable` for later disconnect. Typed per-signal helpers generated by phases 04/09 (`connect_pressed(button, f)`), equivalent to C# events (`button.Pressed += OnPressed`).
3. **Auto-disconnect**: connections whose target is a freed `GodotObject` (closure capturing a script instance or explicit target) are removed like Godot does for C# delegates whose target is a `GodotObject` (`Callable.get_object`). Document the rule for capture-less closures.
4. **Emitting**: `emit_signal(obj, :name, args...)` and typed `emit_<name>` helpers.
5. **Main-thread scheduler** (`GodotSynchronizationContext` parity): Julia `Task`s started via `Godot.@async_godot` (or `godot_task(f)`) run cooperatively on the main thread; continuations after `wait` resume on the main thread during `JuliaLanguage::_frame` (process frame), never on Julia worker threads. Non-main threads can `Godot.post(f)` to the main thread.
6. **Awaiting signals**: `to_signal(obj, :timeout)` returns an awaitable; `wait(to_signal(...))` (or `@await`) suspends the current Godot task and returns the signal arguments as a tuple, matching `await ToSignal(...)` returning `Variant[]`. If the source object is freed, the waiter is resumed with an error/cancellation like C#.
7. **Common awaits**: helpers for `await get_tree().process_frame`, `create_timer(t).timeout`, tween `finished`.
8. **Deferred**: `call_deferred(obj, :method, args...)`, `call_deferred(f)` for Julia callables.
9. **Exceptions in tasks**: unhandled exceptions in Godot tasks are reported via `push_error` with stack trace (C# reports unobserved task exceptions).
10. **Worker threads** (`Task.Run` / `WorkerThreadPool` parity): `add_task(WorkerThreadPool, f)` / `add_group_task(...)` accept Julia callables (adopting engine worker threads), `Threads.@spawn` work can hand results back with `Godot.post`, and the release queue is flushed every frame on the main thread. Follow the threading rules in ADR 0007.

## Tests

- Signal connected to a closure fires; disconnect works; freed target auto-disconnects.
- `wait(to_signal(timer, :timeout))` resumes on the main thread after the timer, inside a headless run.
- Awaiting a signal on an object that gets freed does not leak or hang.
- Typed emit/connect helpers type-check arguments.
- A `WorkerThreadPool` task running a Julia closure completes and posts its result to the main thread.

Update parity rows 3.10, 3.11, 4.10, 6.1–6.6.
```

## Anatomy of the Prompt

### Naming the C# Classes Instead of Describing Behavior

The behavioral reference lists six C# files:

- `Signal.cs`,
- `SignalAwaiter.cs`,
- `GodotSynchronizationContext.cs`,
- `GodotTaskScheduler.cs`,
- `DelegateUtils.cs`,
- `Callable.generics.cs`.

Requirement 5 even carries one of them in its heading: *"Main-thread scheduler (`GodotSynchronizationContext` parity)"*.

Why name classes instead of describing behavior? Because a concurrency model is hard to describe precisely in prose. "Continuations run on the main thread" leaves a lot open:

- *When* do they run? Immediately, at the next frame, at the end of the frame, or whenever the scheduler gets around to it?
- What happens when a continuation is posted from a worker thread?
- What happens to tasks whose awaited object disappears?

The C# classes answer all of those questions in a few hundred lines of code that the agent can read.

Naming them turns a vague concurrency requirement into a **port of a known design**, with Julia primitives instead of .NET ones.

### "Never on Julia Worker Threads"

Requirement 5 holds the phase's most important constraint, in four words. Continuations resume on the main thread *"never on Julia worker threads"*.

By default, Julia's scheduler is free to move a task to any thread. That's great for throughput. It's catastrophic for game code, which may touch the scene tree after any `await`.

The prompt rules out the default behavior explicitly. That forces the agent to find the Julia mechanism for pinning tasks to one thread.

### A Policy Question Left to the Agent, with a Documentation Requirement

Requirement 3 says freed targets disconnect automatically, like C# delegates whose target is a `GodotObject`.

But Julia closures don't have a `Target` property the way C# delegates do. So the prompt adds: *"Document the rule for capture-less closures."*

You've seen this pattern before, in phases 2 and 4. Where the reference has no direct answer, have the agent **choose a policy and write it down**.

### Edge Cases as Requirements

Requirements 6, 9 and 10 cover the cases a happy-path implementation would skip:

- what happens to a waiting task when the awaited object is freed (*"resumed with an error/cancellation"*);
- what happens to an exception in a task nobody is watching (*"reported via `push_error` with stack trace"*);
- how worker-thread results get back to the scene tree (*"hand results back with `Godot.post`"*).

The tests mirror them one to one.

Look in particular at *"Awaiting a signal on an object that gets freed does not leak or hang"*. Most of us wouldn't think to write that test until someone reports a game that slowly fills up with orphaned tasks.

### Two Sentences Added by Phase 7

The end of requirement 10 reads: *"and the release queue is flushed every frame on the main thread. Follow the threading rules in ADR 0007"*.

Phase 7 (chapter 10) added those sentences. That phase built the release queue but had no per-frame hook to drain it, so it wrote the job into this prompt. Phase 10 found the requirement waiting.

## What the Agent Built

### Julia's Analog of `Delegate.Target`

For auto-disconnect, Godot needs to know which object a Callable "belongs to". If that object is freed, Godot removes the connection.

C# uses the delegate's `Target`. Julia closures are structs whose fields are the captured variables. So the agent wrote the analog by inspecting those fields:

```julia
"""
    callable_target(f) -> Union{Nothing, GodotObject}

The engine object a Julia callable is bound to (C#: `Delegate.Target`): `f` itself if it is an engine object, else
the first engine object captured by a closure or stored in a callable struct. A Callable made from `f` is tied to it,
so Godot removes connections through it when the target is freed. Functions and closures that capture no engine
object have no target; their connections last until disconnected or until the emitting object is freed.
"""
function callable_target(@nospecialize(f))
    f isa GodotObject && return f
    T = typeof(f)
    isstructtype(T) || return nothing
    for i in 1:fieldcount(T)
        isdefined(f, i) || continue
        x = getfield(f, i)
        x isa Core.Box && (x = isdefined(x, :contents) ? x.contents : nothing)
        x isa GodotObject && is_instance_valid(x) && return x
    end
    return nothing
end
```

The docstring states the rule for capture-less closures that requirement 3 asked for. The ADR repeats it.

Even the `Core.Box` line encodes Julia knowledge. A captured variable that is reassigned inside a closure is stored in a **box**, so the target may be one level deeper.

### The Scheduler: Julia's Own, with Sticky Tasks

The agent did not write a scheduler. It used Julia's, with one change.

Godot tasks are **sticky** to Julia thread 1, the thread Godot's main loop runs on ([`scheduler.jl`](../../julia/Godot/src/async/scheduler.jl)):

```julia
function godot_task(f)
    t = Task(() -> run_godot_task(f))
    t.sticky = true
    ccall(:jl_set_task_tid, Cint, (Any, Cint), t, MAIN_TID - 1)
    Threads.atomic_add!(LIVE_TASKS, 1)
    on_main_thread() ? yield(t) : schedule(t)
    return t
end
```

Here's the lifecycle of a Godot task started on the main thread:

- It runs immediately, up to its first `wait`.
- After that, it can only resume when the main thread yields to Julia's scheduler.
- The main thread only does that at one point in each frame: in `pump_frame!()`, called from `JuliaLanguage::_frame`.

```julia
"Run posted functions and resume ready Godot tasks; called by the native host every process frame."
function pump_frame!()
    on_main_thread() || return nothing
    jobs = @lock POSTED_LOCK (isempty(POSTED) ? Any[] : splice!(POSTED, eachindex(POSTED)))
    for f in jobs
        try
            Base.invokelatest(f)
        catch e
            Runtime.report_unhandled(e, catch_backtrace())
        end
    end
    if LIVE_TASKS[] > 0 || Runtime.debug_server_running()
        ...
        for _ in 1:MAX_PUMP_ROUNDS
            yield()
            main_runnable() || break
        end
    end
```

Each frame, the pump works in this order:

- runs the functions queued with `post(f)` from any thread;
- yields to ready tasks for a bounded number of rounds;
- flushes the release queue from chapter 10.

This is a direct translation of `GodotSynchronizationContext.ExecutePendingContinuations`. Continuations always run on the main thread, at a well-defined point of the frame.

The ADR is honest about the consequence: *"`await` latency is at least one frame, as in C#."*

The bounded loop (`MAX_PUMP_ROUNDS = 16`) protects the frame from a task that keeps rescheduling itself.

The lines that mention the debug server came later, in phase 13. The debugger's socket tasks needed the same pump.

### Awaiting Signals, Including the Unhappy Path

`to_signal(obj, :sig)` connects a one-shot Callable that wraps a small **awaiter** object. `wait` blocks the current task on an event until the signal fires ([`awaiters.jl`](../../julia/Godot/src/async/awaiters.jl)).

The interesting part is what happens when the signal *never* fires, because the emitter was freed.

In chapter 9, phase 6 added a hook that runs when Godot frees a custom Callable:

```julia
"Hook run when Godot releases the last copy of a custom Callable wrapping `f` (any thread)."
callable_freed(@nospecialize(f)) = nothing
```

Phase 10 specializes it for the awaiter:

```julia
# The one-shot connection is released after the emission, or when the emitting object is freed (then: cancel).
function Runtime.callable_freed(a::SignalAwaiter)
    if (@atomic a.args) === nothing
        @atomic a.cancelled = true
        notify(a.event)
    end
    return nothing
end
```

If Godot frees the connection before the signal fires, the awaiter is cancelled. Then `wait` throws `SignalCancelled` in the waiting task.

`godot_task` treats that exception as a normal end:

```julia
    catch e
        # A task waiting for a signal of a freed object ends silently, like a canceled C# task.
        e isa SignalCancelled || Runtime.report_unhandled(e, catch_backtrace())
```

This is a **deliberate improvement over the reference**, and ADR 0010 says so:

> C# leaves such awaits pending forever; we end them so nothing leaks (tested by task and pin counts).

The prompt said *"resumed with an error/cancellation like C#"*. The agent found that C# doesn't actually do that. So it did better, and recorded the difference instead of copying a leak.

One more guard protects you from a classic mistake:

```julia
        on_main_thread() && !in_godot_task() &&
            error("waiting for signal $(a.signal) on the main thread outside a Godot task would block the engine; " *
                  "start a task with godot_task/@async_godot")
```

Waiting on the main thread outside a Godot task would block the engine's frame loop forever. The error message tells you what to do instead.

Helpers cover the common awaits from requirement 7:

- `next_frame(node)`,
- `next_physics_frame(node)`,
- `delay(node, seconds)`.

Tween `finished` works with `to_signal` directly.

### Worker Threads

`add_task(WorkerThreadPool, f)` and `add_group_task(...)` accept Julia closures. Engine worker threads are adopted on their first call into Julia. Results go back with `post(f)`.

Some engine methods *block*: `wait_for_task_completion`, `Mutex.lock`, `Semaphore.wait`, `OS.delay_*`, … These are generated with the GC-safe `ptrcall` from chapter 6.

Why does that matter? A main thread blocked waiting for a worker never stalls a garbage collection that the worker needs.

## Where Reality Pushed Back

### Two Bugs in the Foundations

The phase 10 report has a section titled *"Two threading bugs fixed"*. Chapter 5 told the full story, so here's a summary.

- **A garbage-collection stall.** Godot worker threads started calling Julia callbacks *directly*, without going through the host's guarded entry points. After that, every later garbage collection stalled. The cause: Julia's own `@cfunction` wrappers adopt an unknown thread but leave it in the GC-unsafe state. The fix routed every callback Godot can call from any thread through a native **trampoline** that parks the thread GC-safe on return. That required ABI v4 and an X-macro list of callbacks in `gdjl_abi.h`.
- **A hang at exit.** Phase 2's prompt prescribed `jl_atexit_hook`. That call suspends all other Julia threads, including adopted engine threads. Godot then waited forever to join them. The host stopped calling it.

Neither bug could have appeared before this phase. No earlier phase let engine worker threads call Julia directly.

Phase 2's invariants were right: every entry goes through the guard, and no exceptions cross C frames. Phase 10 found entry points that bypassed them, and the fix extended the invariant to cover them.

The lesson: foundations get tested by the first phase that leans on them hard. Expect to revisit them then.

### A Flaky-Test Trap

The leak check for cancelled awaits compares task and pin counts before and after.

Comparing them for *equality* would be wrong. Releases from *earlier* tests land asynchronously, whenever the garbage collector runs. So counts can drop during the test.

The test says what it really means:

```julia
        # Counts may drop meanwhile (earlier callables being released) but must not grow.
        check(Godot.live_task_count() <= tasks && Godot.Runtime.pin_count() <= pins,
              "no leaked tasks or pins (tasks $tasks -> $(Godot.live_task_count()), pins $pins -> $(Godot.Runtime.pin_count()))")
```

The agent recorded the rule in its memory notes: *"Leak checks on pin counts must be monotonic (<=): earlier releases land asynchronously"*.

The report also notes that the signals project *"passed three runs in a row"*. That's a sensible check for a test suite full of timing.

### A Script Method Must Not Return a Task

Look at how the test script starts:

```julia
Godot._ready(self::SignalsTest) = (godot_task(() -> run_tests(self)); nothing)
```

The trailing `nothing` is not decoration.

Without it, `_ready` would return the `Task` that `godot_task` creates. The script bridge would then try to convert that task into a Variant for Godot.

The rule became explicit later, during phase 16's demo ports (chapter 19). There, C# `async void` event handlers had to become Julia methods that start a Godot task and return `nothing`.

The memory note: *"Script methods must not return a Task (C# async void -> return nothing)."*

## Techniques to Reuse

- **Name the reference classes for concurrency.** A scheduler is easier to port from `GodotSynchronizationContext.cs` than to specify in prose.
- **Rule out the dangerous default.** "Never on Julia worker threads" forces the agent past the runtime's default behavior.
- **Prefer the runtime's machinery, constrained.** Sticky tasks on Julia's own scheduler beat a hand-written scheduler.
- **Improve on the reference when it leaks, and say so.** Cancelling orphaned awaits is a documented, tested deviation.
- **Write monotonic leak checks.** With asynchronous releases, assert "must not grow", not "must be equal".
- **Expect foundations to break under new load.** When a phase adds a new kind of caller (worker threads), re-check the invariants of the layers below.
