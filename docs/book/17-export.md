# 17. Export: Shipping a Language Runtime

Up to now, everything has run inside the Godot editor or a headless engine on your own machine. Julia is installed there. Packages live in your depot. The bindings are compiled into Julia's package cache.

A player has none of that.

When you export a game, the result must start on a machine that has never seen Julia. It has to start quickly. And it must not depend on anything from your development environment.

**How C# solves it:** it publishes the game's assemblies and the .NET runtime into a `data_<name>_<platform>_<arch>/` folder next to the executable. Release builds can optionally be precompiled (**ReadyToRun**) or fully compiled ahead of time (**NativeAOT**).

Phase 14 builds the Julia equivalent. Two things make it stand out:

- It has the longest-running commands in the project, measured in many minutes per export.
- It contains the clearest example of a requirement that turned out not to be feasible, and was recorded honestly instead of faked.

The phase builds on the editor plugin infrastructure (chapter 15), the script loader (chapter 11) and everything the runtime needs at startup (chapter 5).

## The Prompt

[`.github/prompts/gdjl-14-export.prompt.md`](../../.github/prompts/gdjl-14-export.prompt.md):

```markdown
---
name: gdjl-14-export
description: "Phase 14: exporting Godot games with Julia scripts — runtime bundling, sysimage/juliac compilation, platform support, debug/release, feature tags."
argument-hint: "Optional: target platform(s) to focus on, e.g. windows linux macos"
agent: agent
---
Implement exporting of games that use Julia scripts. Focus platforms: `${input:platforms:windows, linux, macos}`. Follow the [project instructions](../copilot-instructions.md). Behavioral reference: `GodotTools/Export/ExportPlugin.cs` (assembly publishing, per-platform runtime bundling, AOT handling, feature-tag defines), `GodotTools/Build/BuildManager.cs` (publish), and the C# section of the export docs.

## Requirements

1. **Export plugin**: `EditorExportPlugin` (Julia, via `Godot.Editor`) that on export:
   - Excludes `.jl` sources from the PCK unless `julia/export/include_sources` is set (C# ships compiled assemblies, not sources).
   - Builds and bundles the compiled Julia payload next to the executable (`data_<project>_<platform>/`, like C#'s `data_*` folder), plus `libjulia` and required stdlib binaries.
   - Bundles the GDExtension library for the target platform/architecture.
2. **Compilation modes** (selectable per preset, `julia/export/mode`):
   - `sysimage` (default): PackageCompiler custom sysimage containing `Godot`, user packages, and all scripts with a precompile workload generated by running the project's scenes headlessly (equivalent to ReadyToRun).
   - `trimmed`: `juliac --trim` shared library (equivalent to NativeAOT) — scripts must be statically resolvable; report unsupported dynamic constructs as export errors.
   - `jit` (debug only): bundle depot + pkgimages, compile at runtime.
3. **Runtime script loading in exports**: scripts resolve to precompiled modules by `res://` path without parsing sources; hot reload disabled.
4. **Debug vs release**: debug exports keep assertions, backtraces with file:line, remote debugger integration; release strips them where possible and uses `-O3`.
5. **Feature tags / conditional code**: `Godot.has_feature(:windows)` at runtime plus compile-time constants for sysimage/trim builds (parity with `GODOT_WINDOWS`, `GODOT_MOBILE`, `GODOT_PC`, `TOOLS` defines). Editor-only code (`Godot.Editor`) excluded from exports.
6. **Platforms**: Windows x86_64 (+ arm64 if Julia supports it), Linux x86_64/arm64, macOS universal or per-arch (code signing/notarization notes for `libjulia`). Android, iOS and Web are out of scope.
7. **Size & startup**: record export size and cold-start time per mode in `docs/perf.md`; set targets.

## Tests

- CI exports the `smoke` and one demo project for each desktop platform in `sysimage` mode and runs them headlessly, asserting expected output.
- `trimmed` mode exports and runs a minimal project.

Update parity rows 1.3, 1.8, 10.1, 10.2, 10.6–10.8.
```

## Anatomy of the Prompt

### Analogies That Carry Requirements

The prompt describes each Julia mode by its C# analog:

- `sysimage` is *"equivalent to ReadyToRun"*,
- `trimmed` is *"equivalent to NativeAOT"*,
- the payload folder is *"like C#'s `data_*` folder"*.

Each analogy transfers a bundle of expectations without spelling them out:

- **ReadyToRun**: code is precompiled for fast startup, but the JIT stays available for anything not precompiled.
- **NativeAOT**: everything is compiled ahead of time, there is no JIT, the output is smaller, and dynamic code is restricted.
- **`data_*` folder**: the runtime ships next to the executable, the game is self-contained, and nothing comes from your development machine.

Current models know .NET. So an agent gets the startup goals, the size trade-offs and the restrictions from three short phrases.

The Julia-specific details (PackageCompiler, `juliac --trim`, pkgimages) then tell it which Julia tools to consider for each.

### A Requirement Whose Feasibility Was Unknown

The `trimmed` mode requirement is ambitious. It asks to compile everything into a standalone library with `juliac --trim`: *"scripts must be statically resolvable; report unsupported dynamic constructs as export errors."*

When we wrote the prompt, nobody knew whether that could work for an embedded script runtime. The test list includes it anyway: *"`trimmed` mode exports and runs a minimal project."*

Notice that the prompt doesn't say "if possible". The project instructions do:

- *"If something C# achieves only because it is an engine module cannot be done via GDExtension, record it as `GAP` in the matrix with a workaround and an ADR,"*
- and every row must move toward `DONE` or be justified.

Together, those rules gave the agent a **sanctioned path for a justified "no"**. As you'll see, it took that path.

### A Parameter and a Scope Fence That Arrived Mid-Project

`${input:platforms:windows, linux, macos}` lets a session focus on the platforms it can actually test.

Requirement 6 ends with a **scope fence**: *"Android, iOS and Web are out of scope."*

That sentence was not in the original prompt. It comes from the one scope decision in the project's session history. We typed it together with the driver command: `/gdjl-00-next skip and remove 10.3, 10.4 and 10.5`. Those three matrix rows were the mobile and web exports.

The agent's report confirmed:

> **Rows 10.3, 10.4 and 10.5 (Android, iOS, Web) are removed**, as you asked, from the parity matrix and from the phase-14 prompt.

Here's the lesson: a scope decision only sticks if it lands in the artifacts the next session reads. This one landed in both the spec (the matrix) and the plan (the prompt).

### Measurement as a Requirement, with Targets

Requirement 7 asks for export size and cold-start time per mode in `docs/perf.md`. Then it adds *"set targets"*.

That small addition matters. Measuring without a target produces numbers. Measuring against a target produces a decision.

## What the Agent Built

The work is spread across a few places:

- [ADR 0014](../adr/0014-export.md) records the design.
- [`docs/export.md`](../export.md) is the guide for game developers.
- The code is split between a native `JuliaExportPlugin` and Julia tools in [`julia/GodotEditor/src/tools/export.jl`](../../julia/GodotEditor/src/tools/export.jl) and [`export_build.jl`](../../julia/GodotEditor/src/tools/export_build.jl).

### The Payload Folder

At export time, the plugin builds `data_<Package>_<platform>_<arch>/` in a child process, so the editor doesn't freeze (chapter 15). It hands the folder to Godot with `add_shared_object`. Godot's desktop exporters copy shared-object directories next to the executable.

The folder holds:

- the Julia runtime libraries,
- the compiled image,
- the game's dependency list,
- any scripts that couldn't be compiled in,
- a `godot_julia_export.cfg` marker.

Script sources in the game's pack become empty stubs, just as C# does with `.cs` files, unless `julia/export/include_sources` is set.

At startup, the native host looks for a `data_*` folder with that marker next to its library (one level up on macOS). If it finds one, it:

- uses that runtime and image,
- ignores the `julia/runtime/*` settings meant for development,
- isolates `LOAD_PATH` and `DEPOT_PATH` to the folder.

You can see this branch in [`julia_host.cpp`](../../native/src/julia_host.cpp). Exported games get *"Only the game's own depot (compiled caches of jit exports) and the bundled runtime's."*

### `sysimage` Mode Without PackageCompiler

The prompt suggested **PackageCompiler**, the standard Julia tool for custom system images. The agent didn't use it. The ADR explains what it did instead:

> The worker runs `julia --output-o` on a build script. … The object file is linked with Julia's bundled `lld` (`Base.Linking.link_image`), so neither PackageCompiler nor a C compiler is needed.

Why bother? PackageCompiler is a third-party package, and on Windows it typically needs a C compiler toolchain for linking. Someone exporting a game should need neither.

Julia itself can write a compiled image as an object file (`--output-o`), and it ships a linker. The agent found a path that uses only what every Julia installation has.

The core of [`export_build.jl`](../../julia/GodotEditor/src/tools/export_build.jl):

```julia
    cpu_target = get(ENV, "GDJL_EXPORT_CPU_TARGET", DEFAULT_CPU_TARGET)
    step("Compiling the system image ($(debug ? "debug" : "release"), cpu target $cpu_target)")
    ...
                     --sysimage=$default_image --project=$project --output-o=$obj --cpu-target=$cpu_target $flags $script`)
    ...
    Base.Linking.link_image(obj, image)
```

The build script loads `Godot` and the project's packages, then calls `Godot.Runtime.precompile_scripts!`. That function:

- evaluates every script into its module (base scripts first, then dependents),
- records the modules by `res://` path,
- precompiles their methods for the concrete instance types.

In the exported game, `load_script!` takes the module straight from that table. No source is parsed, and hot reload is unused, as requirement 3 asked.

This also differs from the prompt. The prompt suggested a precompile workload *"generated by running the project's scenes headlessly"*. Precompiling every script method for its concrete type covers the same ground, without having to run the game during the export.

### Scripts That Can't Be Compiled In

Some scripts can't be evaluated at build time because their top-level code needs the running engine. For example: `const ITEM = load("res://item.tres")`.

The ADR's answer is **graceful degradation**. Such scripts:

- produce an export *warning*,
- ship as sources in the payload's `scripts/` folder,
- are evaluated at runtime, where the JIT is still available.

This is exactly the ReadyToRun trade-off the prompt's analogy implied: precompile what you can, keep the JIT for the rest.

### `jit` Mode, Debug vs Release

**`jit` mode** (debug exports only) ships package sources inside a depot, so the compiled package caches stay valid when the folder moves. It also ships the stock system image. Scripts run from source.

It exports in about two minutes instead of ten. That matters a lot while you're iterating.

The build configurations differ like this:

- **Debug** images are built with `-O2 -g1`. They keep `res://` file:line in backtraces and the debug server from chapter 16.
- **Release** images use `-O3 -g0`.

### Feature Tags as Compile-Time Constants

Requirement 5 asks for the equivalent of C#'s `#if GODOT_WINDOWS`. The agent implemented it with a macro that behaves differently depending on *when* it is expanded ([`object/scripting.jl`](../../julia/Godot/src/object/scripting.jl)):

```julia
macro feature(tag)
    t = tag isa QuoteNode ? String(tag.value) : tag isa Union{String, Symbol} ? String(tag) :
        throw(ArgumentError("@feature expects a literal tag such as :windows"))
    b = Runtime.EXPORT_BUILD[]
    b === nothing || return t in b.features
    return :($(GlobalRef(Godot, :has_feature))($t))
end
```

Here's how it works:

- **During an export build**, `EXPORT_BUILD[]` holds the preset's feature list. So `@feature(:windows)` expands to a literal `true` or `false`, and Julia's compiler removes the untaken branch from the system image.
- **Everywhere else**, it expands to a runtime `has_feature` call.

One macro gives you both of the behaviors requirement 5 asked for.

### Host Platform Only

The image and runtime are those of the editor's own Julia. So a preset for another OS or architecture fails with an explanation.

Julia payloads cannot be cross-compiled. The ADR states this plainly, and the test runner's header repeats it: *"Exports are made for the host platform: Julia payloads cannot be cross-compiled."* CI is expected to export on each desktop OS.

## Where Reality Pushed Back

### `juliac --trim` Was Not Feasible

The most important outcome of the phase is a negative one. ADR 0014 records it as such:

> **No `trimmed` mode (`juliac --trim`, the NativeAOT analog).** Trimming requires code that is statically resolvable and free of `eval`. The script runtime defines classes with `Core.eval`, dispatches dynamically on script types and keeps the JIT for scripts that are not compiled in. Parity row 10.6 therefore stays PARTIAL, and `sysimage` is the supported AOT mode.

The prompt asked for a mode and a test. The agent analyzed why the mode cannot work for this architecture.

The whole script model of chapters 11–14 rests on evaluating code at runtime:

- a module per script,
- classes defined with `Core.eval`,
- hot reload.

Trimming forbids exactly that.

Think about the alternatives. A trimmed mode that silently fell back to something else would have looked like success. So would a test that only checked that an export *started*. Instead, the matrix row said `PARTIAL` with the reason, and the closest available mode is named as the supported one.

Is this a `GAP` or a `PARTIAL`? The agent chose `PARTIAL`. Its reasoning: ahead-of-time compilation *is* provided (by `sysimage`), and only the trimming part is missing.

That's a **judgment call**, written down where a reviewer can disagree with it. That is the point of writing it down.

And the phase 17 audit did disagree. Trimming will not become possible by finishing work, so the audit reclassified row 10.6 as a `GAP` with `sysimage` as the workaround (chapter 20).

### Long-Running Builds Change How an Agent Works

The numbers from [`docs/perf.md`](../perf.md):

| Mode | Export time | Payload (`data_*`) | System image | Warm Julia startup |
|------|------------:|-------------------:|-------------:|-------------------:|
| sysimage, debug | 672 s | 787 MiB | 393 MiB | 0.70 s |
| sysimage, release | 612 s | 723 MiB | 329 MiB | 0.70 s |
| jit, debug | 115 s | 796 MiB | — | 1.2 s |

Ten minutes per export, with three configurations to test, changes the agent's working rhythm.

The session history shows the pattern:

- The agent starts builds in the background.
- It writes documentation while they run.
- Terminal notifications wake it when they finish.

> The system image is still compiling (the multi-versioned CPU target makes it slower). I'll wait for the export run to finish.

> The documentation and matrix are updated. I'll wait for the final export run to finish before running the regular suites, since they compete for the CPU and the addon DLLs.

That second message shows **operational judgment**. Running the integration suite *during* an export would slow both down. On top of that, on Windows the running export holds the addon DLLs open (the ENOTEMPTY lesson from chapter 15). Waiting was the right call.

Two levers keep iteration bearable:

- The `jit` mode exports in about two minutes.
- `GDJL_EXPORT_CPU_TARGET=generic` builds a single-target image in about 6.5 minutes, instead of about 11 for the default multi-versioned image.

The test runner's default timeout is two hours (`GDJL_TEST_TIMEOUT`, 7200 s). That number says a lot about this phase.

### Windows Path and Archive Limits

Two Windows limits surfaced while assembling the payload. Both went into the agent's memory notes:

- **MAX_PATH.** The Julia standard library contains deep test folders. When copied into an export directory, they push paths past Windows' traditional 260-character limit. The payload copy skips them:

  ```julia
      shipped(rel) = !any(in(("test", "docs")), splitpath(rel))
  ```

- **Extracting the export templates.** The official templates archive (1.28 GB, downloaded and checksum-verified into `.tools/godot/`) must be unpacked to get the template executables. The system `tar` failed on drive-letter paths. So the test runner uses the `7z` binary that Julia's `p7zip_jll` package provides, which works the same on every OS.

### World Age in Runtime-Evaluated Scripts

In `jit` exports, and for scripts that couldn't be compiled in, scripts are evaluated *after* the calling code was compiled.

Julia's **world age** rules then hide the new methods from already-running code until that code explicitly asks for the latest world. The export test shows the idiom:

```julia
        B = Godot.script_type("res://Boss.jl")
        # In jit exports the script was just evaluated, so its methods are newer than this task's world.
        b = Base.invokelatest(B)
```

The report flagged this as something the phase 16 user guide must explain. [`docs/user/julia_export.md`](../user/julia_export.md) now does.

### Honest Remaining Items

The phase 14 report ends with a list that's worth reading as a model:

> - **Linux/macOS exports and macOS signing** have not been run; that waits for CI in phase 15.
> - **Export size:** about 400 MiB of each `data_*` folder is runtime libraries kept so the JIT still works. Trimming unused ones (OpenBLAS, the duplicate libstdc++) is a follow-up.
> - **One editor crash:** the headless editor crashed once on exit after a failed jit export. It didn't recur in later runs, and the cause is unknown.

The last item is the one most reports would leave out. A crash that happened once and didn't recur is easy to forget. Recording it, with "the cause is unknown", leaves a trail if it comes back.

The same report also mentions a fix outside the phase's scope. The debugging frame filter from chapter 16 misidentified the Godot package's own frames when the package had been compiled under a path alias (a directory junction). It now identifies them by module instead of by file path.

The takeaway: path assumptions break in more ways than any single test anticipates.

## Closing the Loop

[`tests/export/run.jl`](../../tests/export/run.jl) does the end-to-end check:

- It writes an export preset per configuration.
- It exports two projects with the headless editor: a dedicated game in [`tests/export/game/`](../../tests/export/game) and the smoke project.
- It runs the exported executables.

```powershell
julia tests/export/run.jl                     # all configurations: sysimage-debug, sysimage-release, jit-debug
julia tests/export/run.jl sysimage-debug      # one configuration
$env:GDJL_EXPORT_CPU_TARGET = "generic"       # faster single-target images while iterating
```

The exported game checks itself ([`Main.jl`](../../tests/export/game/Main.jl), tagged `# parity: 1.8, 9.4, 10.1, 10.2, 10.7, 10.8`):

```julia
        check(Godot.has_feature(:template), "running an exported template")
        check(!Godot.@feature(:editor), "@feature(:editor) is false in exports")
        check(Godot.@feature(:debug) == debug && Godot.@feature(:release) == !debug, "debug/release feature")
        ...
        if mode == "sysimage"
            check(haskey(R.PRECOMPILED_SCRIPTS, "res://Main.jl"), "Main.jl compiled into the system image")
            ...
            check(!haskey(R.PRECOMPILED_SCRIPTS, "res://Dynamic.jl"), "Dynamic.jl not compiled (needs the engine)")
            check(Base.in_sysimage(Base.PkgId(Godot)), "Godot is in the system image")
        end
        check(isempty(Godot.get_file_as_string(Godot.FileAccess, "res://Main.jl")) == (mode == "sysimage"),
              "script sources are stubs in sysimage exports")
```

It verifies that:

- the right scripts were compiled in,
- the engine-dependent one wasn't,
- sources became stubs,
- inheritance and methods work in the exported build,
- the runtime fallback evaluates `Dynamic.jl` from source.

One small detail: the exported game prints its own `GDJL_TEST_RESULT` line. The test-runner package is not a dependency of the game, so it isn't in the image.

The phase 14 report: six of six export runs passed on Windows, and all eleven integration projects still passed afterwards.

## Techniques to Reuse

- **Use analogies that carry requirements.** "Equivalent to ReadyToRun/NativeAOT" transfers startup, size and restriction expectations in a few words.
- **Give infeasible requirements a sanctioned exit.** A project-level rule ("move toward DONE or justify in an ADR") lets the agent answer "not possible, here's why" instead of faking a mode.
- **Prefer what every installation already has.** Julia's own `--output-o` and bundled linker beat a third-party package that needs a C toolchain.
- **Degrade gracefully, and say so.** Scripts that can't be precompiled warn, ship as source, and still run.
- **Plan for long-running commands.** Run builds asynchronously, work in parallel, and don't compete with your own builds for CPU or file locks.
- **Report the unexplained.** "Crashed once, didn't recur, cause unknown" belongs in the report.
